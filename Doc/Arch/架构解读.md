# MyKVM 架构与功能逻辑解读

- 日期：2026-10-13
- 分析基线：v0.9.13 / main@0f93671（约 3.8 万行：Rust 约 3.2 万行，前端约 6 千行）
- 方法：五路并行代码深读（lib.rs / input.rs / 传输与剪贴板子系统 / Windows 原生栈 / React 前端），关键结论经人工抽查验证（端口常量、命令计数、IPC 帧格式等）
- 配套文档：[分级优化方案](./Rfc/分级优化方案.md)

## 一、项目定位与技术栈

MyKVM 是一个**软件 KVM**（用网络替代硬件 KVM 切换器）：同一局域网内的多台 Mac/Windows 机器，把光标移出屏幕边缘即可切换到另一台机器，键盘跟随、剪贴板（文本/图片/富文本/文件）自动同步。

- 后端：Rust + Tauri 2，平台原语大量使用裸 FFI（Win32 / objc_msgSend）
- 前端：React 19 + Vite，TypeScript，单组件控制台
- 辅助进程：input-helper（独立 Windows 服务二进制，SYSTEM 权限注入）
- 定位声明：**可信局域网原型**，未针对不可信网络加固（README 已明示）

## 二、总体架构

```
┌─────────────────────────────────────────────────────┐
│ 前端 React (src/)                                    │
│  App.tsx 单组件控制台 ←─ 2s 轮询 + 3 个事件 ──┐      │
│  desktopApi.ts 桥接层（38 个 invoke，浏览器可降级）│      │
└──────────────────────┬──────────────────────────┘      │
                       │ Tauri IPC                        │
┌──────────────────────▼─────────────────────────────────┴───┐
│ Rust 后端 (src-tauri/src/)                                  │
│  lib.rs (1.22万行) —— 编排中枢：状态/发现/配对/剪贴板/文件传输 │
│  input.rs (1.12万行) —— 输入捕获→编码→传输→解码→注入运行时    │
│  quic_transport.rs —— 单 UDP 端口上的 QUIC/TLS1.3 传输      │
│  平台层：windows_*.rs / *_macos / input-helper(独立 SYSTEM 进程) │
└─────────────────────────────────────────────────────────────┘
        │ UDP 47833 明文发现        │ UDP 47834 QUIC 加密（输入+剪贴板+文件）
```

**前后端分工**：邻接判定、边缘切换、注入全部在后端；前端只负责布局编辑（纯函数吸附算法）、设备管理和设置表单。

**状态同步**：后端仅 emit 3 个事件——`runtime-state-changed`（RuntimeStatus 全量推送，lib.rs:123）、`file-transfer-progress`（100ms 节流，lib.rs:124）、`clipboard-paste-error`（lib.rs:3709）；其余靠前端 2 秒轮询兜底（App.tsx:672），双通道冗余。

## 三、协议设计

### 3.1 三条通道

| 通道 | 端口 | 语义 | 实现 |
| --- | --- | --- | --- |
| 发现 | UDP 47833（`mykvm.discovery.v1`） | 明文广播 announce/probe/reply、配对握手 | 常驻线程 3s 广播，90s TTL 判在线（lib.rs:65-78） |
| 输入 | UDP 47834 QUIC **datagram**（`mykvm.input.v1`） | 鼠标/键盘/滚轮，低延迟容忍丢包 | 16KiB 上限，发送队列丢弃旧包（quic_transport.rs:30） |
| 剪贴板/文件 | 同一 QUIC 连接 **stream**（`mykvm.clipboard.v1` / `mykvm.file-transfer.v1`） | 可靠有序传输 | 48MiB 上限，单流"全量写→ok/reject 应答"（quic_transport.rs:33, 930） |

端口漂移策略：发现端口被占用时在基端口 +8 范围内扫描（`DISCOVERY_PORT_SPAN`，lib.rs:72）；QUIC 端口默认取发现端口 +1，绑定带 SO_REUSEADDR、向上扫 64 个（quic_transport.rs:541-555）。

### 3.2 安全模型

- 每端启动时用 rcgen 生成自签名证书并持久化（`quic-transport-cert.der/key.der`），公钥 = 证书 DER 的 base64（quic_transport.rs:494-539）。
- 连接方 `PinnedCertVerifier` 逐字节 pin 对端证书，且仍用 ring 验证 TLS 1.2/1.3 握手签名——防"只比对字节"绕过（quic_transport.rs:599-664）。
- 配对码确认后的 `pair_secret` 只走加密 QUIC 流传输（lib.rs:9344-9383）；授权校验为"同集群 + pair_secret"（lib.rs:8235-8266）。
- **已知弱点**：发现通道明文无认证；`pair_secret` 为明文等值比较非恒定时间（lib.rs:8249-8251）；无凭据输入包按源地址 5s 放行（input.rs:166-185）。

## 四、后端子系统

### 4.1 编排中枢 lib.rs（12,257 行，其中约 2,000 行为单元测试）

**应用状态**：核心结构 `AppRuntime`（lib.rs:642-677，35 个字段）经 `app.manage()` 托管，分四类——布局/运行时（`layout` 与硬件探测基线 `native_layout`）、网络/对端（`peers`、`quic_transport`、`file_transfers`）、停止信号（三个 `Arc<AtomicBool>`）、剪贴板去重回声（签名 + 1200ms 宽限）。锁策略刻意"快照而非持锁"（lib.rs:895-906 注释）。持久化载体 `LayoutState`（lib.rs:270-317）含角色、集群、配对控制器、各项开关与快捷键。

**Tauri 命令**：39 个 `#[tauri::command]`（注册表 lib.rs:3860-3900），按域分组：状态诊断 5、布局设置 1、运行时启停 3、发现配对 6、剪贴板 3、文件传输 2、输入服务 4（Windows）、远程运维 2、窗口 UI 6、杂项 7。

**线程模型**（全部 std::thread + AtomicBool 停止标志，无 tokio 常驻任务）：发现线程（3s 周期）、输入运行时线程组、剪贴板轮询线程（150ms）、锁屏同步线程（1s）、传输临时文件清理线程（30s）、单实例事件监听（Windows 命名事件）、macOS 光标/窗口/显示器 watcher、macOS 边缘拖拽 worker；一次性 `thread::spawn` 处理异步回复；唯一 tokio 任务是请求式更新（lib.rs:8345）。

### 4.2 设备发现与配对

- **发现**：常驻线程每 3s 广播 announce（255.255.255.255 + 各网卡 /24 定向广播，lib.rs:9917-9923）并探测已知目标；合并进 `peers` 时刷新 `last_seen_ms`，超 90s 剔除并同步 `devices.online`（lib.rs:9551-9565, 9877-9898）。报文为 msgpack 编码的 `DiscoveryPacket`（lib.rs:9018-9030）。
- **角色模型**：客户端是被动方——未配对时隐藏集群 ID、不广播 input_ready，只应答已配对服务端（lib.rs:9115-9129）；服务端是控制方，可请求对端日志/更新/锁屏/拉剪贴板（PeerRequest，lib.rs:8223-8228）。
- **配对流程**：服务端 `pair-request` → 客户端生成 6 位码（60s TTL、5 次尝试限制，lib.rs:9741-9805）弹窗 → 服务端经**加密 QUIC 流**回 `pair-confirm` → 客户端把对端传输公钥写入 `paired_controllers`，实现证书绑定（lib.rs:9344-9383）。
- **连接管理**：无显式"连接"命令，QUIC 传输按需创建、`warm_quic_peer` 发空 datagram 预热（lib.rs:9103-9113）；退出/升级时主动 CONNECTION_CLOSE 让对端立刻重连（lib.rs:1440-1450）。

### 4.3 输入运行时 input.rs（11,229 行）

**数据结构**：`InputTarget`（每条"本机屏 × 远端屏 × 贴边"目标，携带配对凭据/修饰键映射/速度，input.rs:207-228）、`ActiveTarget`（当前被控会话快照）、平台上下文（macOS `CGEventTap` 上下文 input.rs:3258 / Windows 钩子上下文 input.rs:3482 经全局槽暴露给回调）。

**捕获（服务端）**：macOS 用 `CGEventTap`（HID + HeadInsert）订阅移动/拖拽/按键/滚轮，另建双 raw tap 屏蔽手势并转发媒体键（input.rs:1246-1320）；Windows 用 `WH_MOUSE_LL` + `WH_KEYBOARD_LL` 低级钩子。编码为借用型 `InputPacketRef`（rmp_serde MessagePack）瘦包发送：配对凭据每 2s 附一次、每 250ms 附带按住键集合、macOS 鼠标移动附单调序列号防乱序（input.rs:2148-2203）。

**屏幕边缘切换（核心体验）**：

1. 目标生成：`touching_edge` 判贴边（容差 80px，input.rs:2047-2093）。
2. 越界判定 `is_crossing_screen`（input.rs:6205）非常保守：需移动增量 ≥1、为主导轴方向、前一位置在边缘 **160px 激活带**内、且触到边缘 1px 内——防止屏幕中部大跳误触发。
3. 落点：入边位移按比例折算成远端屏内坐标（input.rs:6127-6144）。
4. 切屏后处理：Windows 立即 `SetCursorPos` 锚定并吞掉首个残余 delta（input.rs:4717）；macOS 先隐藏光标再解耦 + 1px 内移钉锚（input.rs:6606-6629）。
5. 返回本机：需 **8px 向外压力**（EdgeReturnGate，input.rs:6312）+ **150ms 冷却**防回弹；返回落点贴边 inset=0。
6. 交还前把被控端光标 park 到裁剪边（input.rs:6537）。

**注入（客户端）**：QUIC datagram 回调 → 锁外解码 → 凭据校验 + 源缓存 → 鼠标序列号防乱序回退 → 坐标按比例映射到本机原生屏（input.rs:2816-3031）→ `dispatch_input_command` 分发。Windows 正常桌面走本进程 `SendInput`；被 `ERROR_ACCESS_DENIED` 拒绝（提权窗口）或处于安全桌面/SecureAttention 时**自动改投 SYSTEM 辅助进程命名管道**（input.rs:2889-2923）；macOS 用 `inject_*` 家族（warp + CGEvent）。

**热键**：`captured_shortcut` 匹配启停/四向切屏/粘贴热键（input.rs:683-707）；`ShortcutKeys` 位图记录物理/逻辑键，切屏前后释放所有逻辑键保证按键配平（shortcut_keys.rs:5-92）。

**守护机制**：guard 线程 200ms 轮询前台应用/全屏/黑名单/Snipaste 截图，暂停时只阻止"进入远端"不回收既有会话（input_guard.rs:206-231）；发送持续失败 1s 强制回本机；held watchdog 对静默 1s 的控制端释放全部按键（input.rs:564-582）；修饰键 mac↔win 重映射随 InputTarget 携带，避免"按下重映射、抬起原始"的 Ctrl 卡死（input.rs:2306-2343）。

**线程模型**：macOS 单捕获线程跑 CFRunLoop；Windows 捕获线程拥有鼠标钩子与消息泵，键盘钩子独立线程，且有"Raw Input 真值源 + 看门狗"双通道自愈（见 4.7）。

### 4.4 QUIC 传输层 quic_transport.rs（1,293 行）

- 独立线程内 2 worker tokio runtime；单 UDP endpoint 同时承担 server/client。
- 连接按 `PeerKey{addr, requested_addr, public_key}` 缓存防连接风暴；connect 超时 2s；keep-alive 3s、idle timeout 10s、initial_rtt 50ms。
- datagram 与 stream 分流是对"输入要低延迟、剪贴板要可靠"的正确建模：datagram 同步发、绝不 await、队列满丢弃旧输入；stream 走信号量限 8 并发的 spawned task，协议为"单向写全量 → 收 ok/reject 应答"，reject 不断开共享连接。
- per-peer 健康表：连续 3 次失败进入 3s 快速失败静默（quic_transport.rs:69-123）。

### 4.5 剪贴板子系统

- **触发**：150ms 轮询（仅当鼠标正控制对端时激活，由输入线程设置 clipboard_target）+ 系统版本号去重（`GetClipboardSequenceNumber` / macOS changeCount）。
- **发送**：读快照 → 签名去重 → 1200ms 回声抑制 → 编码 `ClipboardPacket`（文本 256KiB / 图像解码后 RGBA 32MiB / HTML+RTF 各 4MiB，base64 膨胀按 4/3 折算，clipboard.rs:3-6）→ QUIC stream 发送，失败指数退避重试。
- **接收**：校验协议/授权/序列号单调 → 带重试写本机剪贴板（10 次 × 50ms）→ 记录签名 + 布防回声；带 paste 意图则直接触发粘贴。
- **平台实现**：Windows 裸 Win32 剪贴板（message-only 窗口做 owner，一次写 CF_UNICODETEXT + HTML Format + Rich Text Format，rich_clipboard_windows.rs:112-164）；macOS 裸 `objc_msgSend` 操作 NSPasteboard（rich_clipboard_macos.rs:57-157）。
- 文件类剪贴板不走剪贴板通道，改走文件传输通道（lib.rs:6710-6775）。

### 4.6 文件/文件夹传输

- **三入口**：前端拖放按钮、macOS 边缘拖拽事件（OLE 失败降级 Desktop 传输）、Windows OLE 捕获回调。
- **发送**：`collect_transfer_files` 收集（文件夹先 walk 校验：拒符号链接、禁 Windows 保留名、深度 ≤64，再打 tar 包保留空目录，folder_transfer.rs:21-112）→ 按 256KiB 分块发 `FileTransferPacket`（start → chunk×N → finish，失败 abort），**每块一个独立 QUIC stream + ack**（lib.rs:7617-7626）。
- **限制**：单文件/文件夹 2GiB（walk 字节和、tar 体积、解包三处校验）；最多 64 个选中项。
- **接收**：按 chunk_index 顺序追加 `.part` 临时文件，完成后 finalize 到唯一路径（Desktop / Transfers / Remote Logs / 拖放暂存）；并发上限 32 个/同源 8 个；30s 巡检清理 5 分钟未动的残留。
- **取消**：transfer_jobs 全局 map id→AtomicBool，发送循环每块检查（transfer_jobs.rs:12-49）。
- **paste 回执**：`clipboard_exchange.rs` 维护 30 分钟有效、绑定对端 transport key、单次消费的 paste token 与文件回执。

### 4.7 Windows 原生栈与 input-helper

**注入**：全部 `SendInput`——鼠标绝对移动用虚拟桌面归一化，失败降级 `SetCursorPos`；自我注入用 `dwExtraInfo` 标记（`KEYBOARD_INPUT_MARKER`）防钩子回环（windows_input.rs:13, 369-397）；SAS（Ctrl+Alt+Del）动态加载 sas.dll 调 `SendSAS`；桌面切换每次 `OpenInputDesktop` 不按名字缓存（同名 Winlogon 桌面对象会更换，windows_input.rs:147-197）。

**提权窗口支持**：普通进程向提权窗口注入被拒 `ERROR_ACCESS_DENIED` → 自动重发到 SYSTEM helper 管道；反向坑也有处理——SYSTEM helper 在普通桌面反而被 Medium 完整性前台拒绝，故正常桌面走本进程（input.rs:2889-2923）。

**键盘双通道自愈**：`windows_keyboard_capture.rs` 管低级键盘钩子生命周期（专用线程安装/卸载/空闲复用）；`windows_keyboard_monitor.rs` 用 Raw Input（RIDEV_INPUTSINK）作为物理键盘独立真值源，`KeyboardHookWatchdog` 对比两路 tick，250ms 判定"钩子安装成功但无回调"并自动重装（windows_keyboard_monitor.rs:43-67）。

**原生拖拽三模块协作**（Windows 独有的完整拖拽体验）：

1. **drop_catcher（边缘接盘）**：隐藏 `IDropTarget` 窗口贴到光标处，捕获本机拖出的 `CF_HDROP` → 传到对端 → 注入 Esc+左键弹起终止本地拖拽 → 置 handoff 标志让钩子真正跨界（windows_drop_catcher.rs:436-486）。
2. **drag（OLE 源）**：对端落地时运行真正 `DoDragDrop`，`IDataObject` 暴露 `FileGroupDescriptorW/FileContents` 虚拟文件，`IStream` 由网络流式填充的 `FileBuffer`（NamedTempFile 磁盘 spool + Condvar 等待数据）支撑，实现边收边供 Explorer 拖放（windows_drag.rs:498-564）。
3. **overlay**：跟随光标的点击穿透分层窗，自绘文件图标 + 进度条，drop 后停靠任务栏直至异步提取完成。

**input-helper 独立进程**（input-helper/，Windows 服务）：单一 exe 三模式——`--service`（SCM 服务，接受 STOP/SESSION_CHANGE）、`--worker`（会话内注入）、headless QUIC 接收器（GUI 进程死后接管网络保持被控）。服务按 `WTSGetActiveConsoleSessionId` 检测会话漂移，用 `CreateProcessAsUserW` 以 SYSTEM 身份向目标会话投放 worker。IPC：每会话命名管道 `\\.\pipe\mykvm-input-s{sid}`（SDDL 仅 SYSTEM + 该会话用户），帧格式为 4 字节 LE 长度前缀 + MessagePack `InputCommand`（shared_input.rs:102-118）。

## 五、前端架构

- **单组件控制台**：全部 UI 集中在 `App` 组件（App.tsx:190-3500，约 3300 行、42 个 useState），无路由无状态库。视图：Onboarding 角色选择、布局画布/设备列表/设置页三个 Tab（客户端角色仅见设置）、配对码表单、传输 Toast、Windows 自绘标题栏。
- **桥接层 desktopApi.ts**：封装约 38 个 invoke 命令与事件监听；非 Tauri 环境返回静态 stub 与内存布局，纯浏览器开发可行（desktopApi.ts:32-113）。
- **布局算法 layout.ts（纯函数、带测试）**：AABB 重叠判定、按主位移轴碰撞吸附（`snapOverlappingScreenPosition`）、80px 边线对齐吸附。注意：**邻接判定与边缘切换不在前端**，实际切换由后端按布局执行。
- **数据模型**：`Device`/`Screen`/`LayoutState`（types.ts）+ `LanPeer`/`RuntimeStatus`/`PerformanceSample`（runtime.ts）。
- **数据刷新**：2s 轮询（runtime+layout）+ 事件订阅混合；性能采样 3s、诊断 5s。
- **快捷键录制 hotkeyInput.ts**：Backspace 清绑定、纯修饰键忽略、无修饰仅功能键可单键、输出 ctrl+alt+shift+meta+key 规范序（hotkeyInput.ts:31-70）。
- **i18n/主题**：静态 `TEXT = { cn, en }` 双语对象无框架；主题三态（浅/深/跟随系统）经 matchMedia + Tauri `onThemeChanged` 双通道。

| 消息 | 通道 | 用途 |

| `DragControlPacket`（start/drop/cancel + files[]） | stream | Windows OLE 原生拖放会话控制 |
| `ClipboardFilesCommit`（ids[] + paste_token） | stream | 远端文件剪贴板落位提交 |

## 七、工程质量评价

### 亮点

1. **热路径纪律**：输入路径极度规避锁（`try_lock` + 250ms 目标缓存），datagram 发送绝不 await，凭据 2s 附一次瘦包；datagram/stream 分流建模正确。
2. **防御性工程密度高**：回声抑制双保险、键盘 hook + Raw Input 双通道看门狗自愈、自我注入 dwExtraInfo 标记防回环、文件名消毒与路径逃逸防护、锁中毒容错、并发上限；代码注释大量记录真实踩坑（鼠标 warp 回环、同名桌面句柄失效、SYSTEM 完整性反向拒绝等）。
3. **分层合理**：协议/平台原语已拆 20+ 模块；layout.ts/hotkeyInput.ts/versions.ts 为带测试纯函数；desktopApi 统一降级层；lib.rs 尾部约 2000 行单元测试，测试覆盖关键纯逻辑。
4. **协议向后兼容意识**：旧字段全部 `#[serde(default)]`，新增能力走 probe 探测降级。

### 主要问题

1. **两个巨型文件**：lib.rs（1.22 万行）是所有协议汇聚点，Windows 服务安装/防火墙等约 1500 行运维逻辑与之同文件；input.rs（1.12 万行）混协议、捕获、注入、拖拽。App.tsx 3300 行单组件、42 个 useState，任一状态变化全树重渲。
2. **全局可变静态多**（input.rs:191-196, 283-289, 483, 529, 3824 等）：会话正确性依赖手工复位与 `Arc::ptr_eq` 清理；`SENDER_HELD` 全局单例在多目标并发时理论上互相污染；`remote_screen_points` 只增不删，长期运行缓慢增长。
3. **性能隐患**：文件传输每 256KB 块单独建 stream 并等全量 ack，2GiB 需 8192 次往返，吞吐受 RTT 支配；32MiB 剪贴板图像 base64 后约 43MiB 贴着 48MiB 流上限；`send_stream_expect_ack` 调用方最长 6s 阻塞。
4. **安全细节**：`pair_secret` 非恒定时间比较；无凭据包 5s 源放行存在伪造窗口；发现通道明文。均在"可信局域网"前提下可接受，与 README 定位一致。
5. **验证盲区**：Windows 拖拽三模块作者自述仅交叉类型检查、未真机验证（windows_drag.rs:16-19）；CI 无 fmt/clippy；`updateLayout` 在 setState 回调内触发保存 IPC，StrictMode 下重复调用。

## 八、一句话总结

协议设计清晰、平台坑位处理相当扎实的早期原型，单机体验的工程密度接近生产级；主要技术债务集中在"编排逻辑过度集中于 lib.rs / input.rs / App.tsx 三处巨型文件"与轮询驱动的状态同步上。演进路径见 [分级优化方案](./Rfc/分级优化方案.md)。
