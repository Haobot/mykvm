# MyKVM 跨设备指针速度对齐方案

- 日期：2026-10-23
- 状态：实施中（P0 已确认：Windows 缩放 250%；P1 单位归一已实现，待 Windows 真机验证）
- 基线：`main @ ffea5f9`（v0.9.13 之后）
- 方法：三路并行只读代码审计（Windows 控制端坐标空间 / macOS 接收与捕获 / 参数链路与协议），关键结论由 Lead 复核；所有行号以 ffea5f9 为准
- 场景：Windows（PROART16，server/控制端，物理鼠标）→ MacBook（client/被控端）
- 现象：控制 Mac 时指针"特别滑"（明显偏快、不易精确定位）；Windows 本地"跟手"

## 0. 结论摘要（TL;DR）

1. **已坐实一个发送端单位错误**：Windows 采集到的 `dx` 是原生物理像素，却被直接累加进"被控端逻辑点"坐标（`src-tauri/src/input.rs:4976-4977`）；同一函数里"进入远端时的落点"却已按逻辑单位归一（`input.rs:6645-6650`）。结果是**被控端 DIP 速度 = 本地 × Windows 该屏缩放比例**（已确认本机 Windows 为 250% → 被控端偏快 2.5×）。
2. **接收端不需要改**：macOS 把 wire `MouseMove{screen_id,x,y}` 忠实解释为"本机该屏逻辑点偏移"，注入是 `warp + CGEvent` 绝对定位（`input.rs:8441-8470`），没有二次加速、DPI 缩放或速度倍率；`pointer_speed` 只在控制端使用。
3. **修复分三阶段**：P1 发送端单位归一（**已实现**：约 30 行 Rust + 8 个单测，不改协议、只升级控制端即生效）；P2 精细倍率/校准（UI 0.25–3.0、0.05 步进，现有 0.5 下限不够）；P3（可选）按屏物理尺寸自动对齐，解决"单位修好后仍有 1.4× 物理偏差"的异构 PPI 残差。
4. **量化**（Windows 缩放 250% 已确认；面板按其 16" 3840×2400 4K OLED 假设）：当前链路被控端物理速度是控制端的 **2.22×（内建屏）/ 3.47×（MateView）**、DIP 速度 2.5×；P1 后分别降到 **0.89× / 1.39×**（逻辑 1:1），内建屏接近一致，MateView 可用设备指针速度 0.75× 微调到约 1.04×。若面板实际为 3200×2000 等规格，方向不变、物理比值略变（§2.5 给公式）。
5. **临时缓解（不改代码，作用有限）**：调低 Windows 系统指针速度或 App 内设备指针速度都会按比例降低 Mac 端速度（用户已验证）。但前者同时改变 Windows 本地手感与加速曲线；后者受当前 UI 下限 0.5× 限制——250% 缩放下"逻辑 1:1"需要 0.40×、MateView"物理一致"需要约 0.29×，**当前档位无法完全补偿**，因此 P1 是必要修复而非可选优化。
6. **非目标**：不改指针加速曲线（保留"继承控制端 EPP/系统加速"的现有手感）、不改线上坐标单位/协议版本、不引入 raw HID 自研加速、不在 macOS 接收端做补偿。

## 1. 需求：什么叫"两侧速度对齐"

### 1.1 用户诉求

同一只物理鼠标：在 Windows 本地移动时"跟手"；越过屏幕边缘控制 Mac 时，Mac 光标移动明显更快、更"滑"。目标：**让被控侧的光标速度与 server（控制端）本地的鼠标速度一致**。

"速度一致"在跨 DPI 场景下没有唯一含义，必须先选定口径。

### 1.2 三种候选口径

记同一段手部移动在控制端本地产生的物理像素位移为 `P`，控制端该屏缩放为 `S`、每物理像素毫米数为 `mmPx_L`；被控屏每逻辑单位（Mac=point）的毫米数为 `R_mm`；用户倍率为 `k`、单位增益为 `u`（P1 前 `u=1`，P1 后 `u=1/S`）。

| 口径 | 定义 | 比值（被控/本地） | 直观感受 |
| --- | --- | --- | --- |
| (a) 物理一致 | 手移动 1 mm，两侧光标都移动 1 mm | `k·u·R_mm / mmPx_L` | 手–光标协调一致，"跟手" |
| (b) 逻辑一致 | 1 控制端 DIP = 1 被控端 point | `k·u·S` | 与 OS 跨 DPI 屏的惯例一致 |
| (c) 屏占比一致 | 同一手势穿越屏幕的比例相同 | `k·u·W_px_L / W_pt_R`（X/Y 各一，通常不同） | 大屏上光标物理更快，穿越屏幕耗时接近 |

### 1.3 推荐

- **默认口径 (b)**：零新增数据、零协议改动，也是 Windows/macOS 自身跨 DPI 显示器时的行为；P1 修复后 `k=1` 即精确成立。
- **终态口径 (a)**：用户说的"跟手/滑"本质是手到光标的物理增益，终态用 P3 按屏自动计算（无数据时回退 (b)）。
- **(c) 不用作默认**：横纵轴比值通常不同（按 250% 缩放，本机内建 0.984/1.023、MateView 1.250/1.333），且会让 28" 屏穿越明显变慢。
- `k`（手动倍率）保留为个体偏好微调，乘在 (b)/(a) 的有效增益之上。

### 1.4 已确认的前提：Windows 显示缩放 250%

P1 的收益直接等于 `S`：本机 Windows 已确认 `S=250%`，即当前被控端 DIP 速度是本地 2.5×，P1 修复后被控端速度约为当前的 0.4×。Windows 原生分辨率未单独确认；本文量化按 PROART16 常见的 16" 3840×2400（16:10、283 PPI）计算，若实际为 3200×2000 等面板，方向不变、物理比值略变（§2.5 给公式）。

## 2. 现状与根因

### 2.1 数据流（当前实现）

```
控制端捕获                     控制端虚拟光标                线上（QUIC datagram）                 被控端注入
WH_MOUSE_LL: 物理像素 x,y  →  active.x/y（被控屏逻辑单位） → MouseMove{screen_id,x,y} 绝对位置 → 逻辑→原生比例映射 → warp/CGEvent 绝对定位
（每帧 warp 回屏心 anchor）      (input.rs:4976-4977)          (shared_input.rs:19, input.rs:7014-7031)   (input.rs:3381-3412, 8441-8470)
```

- wire 坐标语义：**以 `screen_id` 为锚的屏内逻辑坐标（0..width-1）**，宽高取被控端广播的逻辑尺寸（`lib.rs:4651-4699` 检测 → `lib.rs:8722-8724` / `8789-8800` 广播 → 控制端 `screens_from_peer` `lib.rs:8582` 合并）。
- 接收端：`map_relative_to_native_axis`（`input.rs:3189-3197`）按"逻辑宽 → 原生宽"比例映射；macOS 的 `platform_native_screen` 是 identity（`input.rs:3216-3219`），故 `absolute = screen.x + x`（point），再 warp + 投递 HID（无加速，Apple 文档：CGWarpMouseCursorPosition "without generating events"）。
- Windows 的 `platform_native_screen` 把逻辑值 ×scale 还原为物理像素（`input.rs:3199-3233`），供 `is_crossing_screen` 等原生几何使用。

### 2.2 根因（唯一错误点）

```rust
// input.rs:4961-4977  handle_windows_mouse_move
let dx = x - anchor.0;                     // WH_MOUSE_LL: 原生物理像素（单帧，见 §2.4）
let dy = y - anchor.1;
...
active_target.x += dx * active_target.target.pointer_speed;   // ← 把物理像素当逻辑单位累加
active_target.y += dy * active_target.target.pointer_speed;
```

对照入边落点——同一套比例换算已经存在却不用于每帧累加：

```rust
// input.rs:6645-6650  crossing_target
let entry_dx = dx * target.layout_local_screen.width.max(1) as f64
    / target.local_screen.width.max(1) as f64;   // = dx / scale
```

- `InputTarget.local_screen` = **平台原生**矩形（Windows 物理像素；macOS point），`layout_local_screen` = 同一块屏的**逻辑**尺寸；比例 ≈ 1/scale（`input.rs:2285-2348`、`3199-3233`；逻辑尺寸来源 `lib.rs:4651-4699,4996-5018`）。
- 35 处 remote-active 期间 dx/dy、x/y 使用点已逐项审计：**只有 `4976-4977` 混用单位**；其余（换边判定、clamp、返回落点、park、发送、日志等）自洽或仅取符号。
- 影响：被控端 DIP 速度 = 本地 DIP 速度 × `S`。本机 250% 时恰好 2.5× 偏快，与"明显偏快、不易精确定位"吻合。

### 2.3 为什么可以断定 Windows 钩子坐标是物理像素

1. 依赖链：Tauri 2.11.2 默认使用 tao 0.35.3 事件循环 → tao 默认 `dpi_aware: true` → `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`（tao `dpi.rs`）；因此 `MSLLHOOKSTRUCT.pt` 与 `SetCursorPos` 都是 per-monitor 原生像素。
2. 仓库内部反证：换边判定 `is_crossing_screen` 用 `target.local_screen`（原生矩形，`input.rs:6689,6724-6769`），若钩子坐标是虚拟化逻辑像素，在缩放 >100% 的屏上永远无法触边；而 warp 回环过滤按坐标精确匹配（`input.rs:4484-4491,5396-5404`）也只有在同一原生空间才成立。实际使用正常 → 同一原生空间。
3. 未验证项：未在 Windows 真机上直接打印对比；措辞按"强证据推断"对待。

### 2.4 每帧回锚点与"继承系统加速"

- 每个移动事件末尾 `set_windows_cursor(anchor)` 把隐藏光标拨回屏心（`input.rs:5116-5118`，anchor=`local_center_point` §`6964-6970,7038-7043`），下一事件 `x = anchor + 该帧移动` → `dx` 是**单帧位移**而非累计；`SetCursorPos` 产生的回环事件由 `CursorWarps` 丢弃（`windows_mouse_motion.rs:4-48`）。
- 钩子看到的是系统指针加速（EPP）之后的位置 → 被控端**继承控制端加速曲线**，这是"Win 本地跟手"的来源，**应保留**；本次只换单位，不碰加速链路。

### 2.5 量化（Mac 屏实测；Windows 缩放 250%，面板按 16" 3840×2400 假设）

| 内建 Built-in Retina | 1512×982 | 3024×1964 | 301.21×195.63 mm | 127.5 | 0.1992 |
| MateView 外接 | 1920×1280 | 3840×2560 | 598.38×398.92 mm | 81.5 | 0.3117 |

| --- | --- | --- |

达到各口径所需的用户倍率 `k`：

| 目标 | 当前链路 | P1 后 @S=250% |
| --- | --- | --- |
| 内建屏物理 (a) | 0.451 | **1.126** |

要点：
- 两块 Mac 屏 points/inch 相差 **1.56×**，P1 后物理对齐所需倍率为 1.13（内建）vs 0.72（MateView）——**单一 per-device 倍率无法同时满足**；终态应按"本机屏 × 远端屏"的 `InputTarget` 粒度自动计算。
- 当前 UI 下限 0.5 在 250% 下连"逻辑 1:1"（0.40）都达不到，更不用说 MateView 物理一致（0.29）——**手动补偿不可行，P1 是必要修复**。

- 用户已验证"降低 Windows 端速度会按比例降低 Mac 端速度"，说明被控端只是忠实复现控制端光标位移，与 `dx` 被直接累加的链路一致。

### 2.6 已排除的因素（无需再查）

| # | 候选 | 结论 |
| --- | --- | --- |
| 1 | macOS 接收端二次加速/缩放/插值 | 无：`platform_native_screen` identity、warp 绝对定位、无平滑代码；14 项逐条排查 |
| 2 | 接收端应用 `pointer_speed` | 无：仅在控制端 `build_input_targets` / 两处捕获累加使用 |
| 3 | wire `screen_id` 不匹配导致落错屏 | 会回退主屏/首屏，但只影响落点，不改变速度；当前 `peer_screen_id` 往返匹配正常（`input.rs:2462-2468`） |

## 3. 方案对比

### 3.1 方案 A：发送端单位归一（P1，必做 → 已实现）

把每帧原生 delta 换算成 layout 逻辑单位后再累加，`pointer_speed` 乘在归一化之后。

- **状态（2026-10-23）**：已实现并提交；macOS `cargo test --lib` 226 项全绿（新增 8 项）；Windows 侧编译由 CI 验证，Windows 真机行为待验收（本机 macOS 无法交叉编译 ring 的 C 代码，`cargo check --target x86_64-pc-windows-msvc` 在依赖构建阶段失败，属工具链限制）。

```rust
// input.rs 新增纯函数（cfg(any(windows, test))，macOS 测试也可覆盖）
fn native_delta_to_layout(target: &InputTarget, dx: f64, dy: f64) -> (f64, f64) {
    let native = &target.local_screen;        // Windows: 物理像素；macOS: point
    let layout = &target.layout_local_screen; // 同一块屏的逻辑尺寸
    (
        dx * layout.width.max(1) as f64 / native.width.max(1) as f64,
        dy * layout.height.max(1) as f64 / native.height.max(1) as f64,
    )
}
// handle_windows_mouse_move 内（原 4976-4977 处）：几何判定仍用原生 dx/dy
let (step_dx, step_dy) = native_delta_to_layout(&active_target.target, dx, dy);
active_target.x += step_dx * active_target.target.pointer_speed;
active_target.y += step_dy * active_target.target.pointer_speed;
```

- 用**宽高比**而非直接读 `scale`：与入边换算 `6645-6650` 完全同源，并自动吸收 `platform_native_screen` 的取整误差（如 1707 逻辑 → 2561 原生）。
- 每块本地屏各自换算：`build_input_targets` 本来就是"本地屏 × 远端屏"生成 target（`input.rs:2307-2344`），Windows 多屏混合 DPI 天然正确。
- **不变量**：几何判定（`is_crossing_screen`、返回 gate）继续用原生 delta，避免改变换边手感——variant A（推荐先做）；variant B（把 gate 阈值也统一为逻辑单位，与 macOS 语义一致）作为可选后续，需真机确认手感。
- 兼容性：wire 语义不变、接收端不改、`PROTOCOL_VERSION=1` 不动。新↔旧任意混跑均可（新控制端 + 旧接收端同样修好；旧控制端保持现状）。
- 主要用户侧风险：曾用 pointer_speed（0.5×/0.75×）补偿过速度的用户，升级后会"再慢一次"，发版说明需提示恢复 1×。此信息无法自动迁移。

### 3.2 方案 B：精细倍率与校准（P2，推荐紧随）

- UI：`src/DeviceSettingsModal.tsx` 的指针速度从 6 档 select 改为 0.25–3.0、步进 0.05 的滑杆/数字输入（保留 1.0 刻度、恢复默认、显示有效值）；`src/i18n.ts` 补模式/说明文案；`src/types.ts`、`src/pairingRepair.ts` 透传。
- 后端：`Device` 增加 `pointer_speed_mode`（standard/manual/auto，`serde(default)`），`sane_input_speed` 维持 0.25–4.0 兜底；`input.rs` 用纯函数计算有效增益，wire 仍以 f64 累加、发送时 round（不要改成整数截断，否则 0.5× 会丢步）。
- 迁移：旧记录无 mode 且 speed==1.0 → standard；speed≠1.0 → manual（尊重既有设置）。
- 该阶段可以先按 per-device 交付；per-screen 覆盖/auto 留到 P3（屏幕 id 稳定性问题见 §3.3）。

### 3.3 方案 C：按屏物理尺寸自动对齐（P3，可选终态）

- 数据：Mac 侧 `CGDisplay::screen_size()`（core-graphics 0.25 已是依赖，无需 TCC）；Windows 侧无直接 API，优先级：**EDID 注册表 best-effort（Chromium `physical_size.cc` 先例）→ 用户手填对角线兜底 → 不做**；WMI `WmiMonitorBasicDisplayParams` 次之；`GetDpiForMonitor` 不可靠。
- 传播：`Screen`/`LanPeerScreen` 增加可选 `physical_width_mm/physical_height_mm`（`#[serde(default)]`）。发现包是 rmp-serde **named map**（`lib.rs:8370-8379`），旧端忽略未知字段、新端缺省 None；仓库有同型先例（d4f323b 给 LanPeer 加字段并注明 backward compatible）。**不要升 PROTOCOL_VERSION**（升版会使旧对端 input_ready=false）。
- 计算：`build_input_targets` 里按每个 InputTarget 计算 `gain_auto = (local_mm_per_DIP) / (remote_mm_per_point)`，缺任一数据回退 standard；对 mm 做合理性校验（0/NaN/宽高比偏差过大 → None）。
- 两块 Mac 屏 points/inch 差 1.56×：**per-screen 是唯一正确做法**（P1 后 1.13 vs 0.72），这也正是 `InputTarget` 已有粒度。
- 代价/风险：Windows EDID 读取是最大工作量（SetupAPI/DisplayConfig 映射、无 EDID/虚拟屏/克隆屏缺失）；屏幕稳定 id 需要单独解决（本地屏 id 目前是 `local-display-N`，会随枚举顺序漂移）；建议数据源标注 edid/manual/estimated 并在 UI 提示"估算值"。

### 3.4 不采用的方案

| 方案 | 不采用原因 |
| --- | --- |
| 接收端按自身屏幕反算 | 接收端不知道控制端物理尺寸，只会引入第二个未知量 |
| 改 wire 单位为物理像素/mm | 需 PROTOCOL_VERSION v2，所有对端同时升级，收益不及发送端归一 |
| 捕获 raw HID 并自研统一加速曲线 | 会改变本地/远端手感、平台工作量大，且用户要的是"和本地一致"，现状继承系统加速恰好满足 |
| 关闭 Windows EPP / macOS 加速 | 不解决单位问题，且 macOS 注入本来就不经过加速曲线 |

### 5.2 真机测量协议（±10% 验收线）

前置：Windows 缩放已确认 250%（改缩放后需重启 MyKVM）；两块 Mac 屏分别测（per-screen 目标不同）。

1. 鼠标垫/直尺上标 200 mm 直线，同一方向连续做 3 次，分别记录：
   - 控制端物理位移 `P` px：用诊断日志累计 `dx`（hidden cursor 被重锚，不能只看最终光标位置）；
   - 被控端位移 `Δpt`：临时 Swift/Quartz 采样 `CGEvent(source:nil)?.location`（5 ms），或用注入侧临时日志首末差。
2. 计算：
   - 口径 (a) 物理比 = `(Δpt × R_mm) / (P × mmPx_L)`，验收 **0.90–1.10**；
   - 口径 (b) 逻辑比 = `(Δpt × S) / P`，验收 **0.95–1.05**（P1 默认应精确 1.0）。
3. 慢推/快甩各 3 次：比值不应随速度漂移（证明仍继承控制端加速、无额外非线性）。
4. 补充：每次进入 Mac 的第一段移动不跳变；快速来回过边 10 次落点/隐藏/park 正常；`k=0.25` 与 `3.0` 极端不丢步。

建议新增 env 门控诊断日志（默认关闭，如 `MYKVM_POINTER_DEBUG=1`）：每 N 帧打印 `screen/gain/dx/remote(x,y)`，用于测量与用户反馈；不在协议内传输、不影响默认行为。

## 6. 兼容性与迁移

- **协议/版本**：P1 不动 wire 单位；P2/P3 只新增 `serde(default)` 可选字段，**不升 PROTOCOL_VERSION**。混合版本矩阵：新控制端+旧被控端=修好；旧控制端+新被控端=保持现状；两端皆旧=现状。
- **升级范围**：P1 只需升级 Windows（控制端）即生效，Mac 可不升级；P3 需要两端都较新才能 auto。
- **用户设置迁移**：P1 后曾用 0.5×/0.75× 补偿的用户需恢复 1×（发版说明 + 设备设置页提示）；P2 引入 mode 时按"speed==1→standard、否则 manual"迁移。
- **已知边界**：Windows 运行中改缩放/分辨率需重启 MyKVM（预存在）；macOS 屏幕旋转时 mm 与逻辑宽高需按旋转交换（P3 未验证项）；本地屏 id 会随枚举顺序漂移（P3 手填/持久化前需稳定 id）。
- **明确不做**：修改接收端、关闭系统指针加速、改 wire 单位、自研 raw HID 加速。
