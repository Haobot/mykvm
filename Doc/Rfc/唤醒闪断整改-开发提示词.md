> **基线**:当前 `main`(开发提示词行号随代码演进漂移时按函数名定位)。

## 1. 问题机制(上一轮遗留,已复现于代码分析)

上一轮 P1-2 的时钟跳变防御(`prune_stale_peer_entries_with_baseline`,lib.rs:10277;`clock_jump_guard_skips_prune`:10293;`CLOCK_JUMP_GUARD_MS = 300_000`:10267)只**跳过一轮** prune。Mac 睡眠超过 PEER_TTL_MS(90s)醒来时:

1. 第一次 prune:检测到前跳 > 300s → 跳过本轮删除,基准更新为 now;
2. 约 0.5s 后第二次 prune:基准已是 now,不再触发跳变保护 → peers 的 last_seen 仍是睡前的,全部超过 TTL → **整批删除**;
3. Win 端下一次 announce(≤3s)才重新合并 → 设备「在线」闪成「离线」再恢复,UI 2s 轮询可能完整看到一次闪断。

同样场景也适用于 NTP 大幅前跳(此时 peers 实际是活的,闪断更冤)。目标:跳变后的宽限期内(≥ 一个 announce 周期)peers 不被批量删掉,唤醒/校时不再闪断;代价(可接受)是真已下线的对端最多多显示在线一个短宽限期。

## 2. 目标 / 非目标

**目标**:检测到时钟前跳(或等效的唤醒)后,peer 存活判定进入一个**短宽限期**(`CLOCK_JUMP_GRACE_MS`,建议 5_000ms ≥ announce 3s + 余量),宽限期内不批量淘汰 peer;宽限期后恢复正常 TTL 语义。行为必须在**所有 TTL 判定点一致**(见 §3.1 第 3 条),不允许出现「devices 显示在线但 discovery peers 计数为 0」的撕裂。

**非目标**:不改 PEER_TTL_MS/announce 周期;不做离线/睡眠状态区分显示(后续需求);不改 wire 协议、QUIC、坑 6 路由。

## 3. 推荐方案(A:宽限期),备选方案(B:last_seen 前移)

### 3.1 方案 A(推荐):统一 stale 判定 + 宽限截止时间

1. 新增 `CLOCK_JUMP_GRACE_MS: u64 = 5_000` 与静态 `PRUNE_GRACE_UNTIL_MS: AtomicU64`(命名可调):
   - `clock_jump_guard_skips_prune` 检出跳变时,除现有日志外设置 `grace_until = now + CLOCK_JUMP_GRACE_MS`;
   - 重复跳变/宽限期内再次跳变 → 顺延 grace_until(幂等)。
2. 新增统一谓词 `fn peer_stale(now: u64, peer_last_seen: u64) -> bool`:`now.saturating_sub(peer_last_seen) > PEER_TTL_MS && now >= grace_until`。**所有**按 TTL 判定 peer 过期的调用点改用它,至少包括:
   - `prune_stale_peer_entries_at`(lib.rs:10297,删除与 retain 两处);
   - `active_peers`(lib.rs:9880,读路径 TTL 过滤)——否则 discovery peers 列表与 devices 在线状态在宽限期内撕裂;
   - 排查其余 `PEER_TTL_MS` 引用点,凡语义是「peer 是否已过期」的一并接入;若是「新鲜度提示」(如 probe 续命的 45~90s 窗口,`peers_nearing_ttl_probe_targets` lib.rs:10323)保持不变。
3. 宽限期**只延缓淘汰,不伪造 last_seen**:announce/probe 到达时照常刷新 last_seen;宽限期结束后,只有真正被心跳续命的 peer 存活。
4. 日志:沿用 `discovery prune skipped after apparent clock jump`,补充 grace_until 信息;宽限期结束若有批量淘汰,info 一条(`discovery prune expired N peers after grace`)。

### 3.2 方案 B(备选,实现更简):检出跳变时把 peers 的 last_seen 前移至 now

语义「睡眠=冻结、醒来=续一个完整 TTL 窗口」,天然对所有 TTL 判定一致。代价:真下线的对端在唤醒后最多 90s 才显示离线。若实现者认为 B 更贴合现有代码结构,可改用 B,但须在交付说明中论证,并满足 §4 全部行为验收标准(把「宽限期」读作「一个 TTL 窗口」)。

## 4. 测试要求(行为验收标准,两个方案通用)

## 8. 补充任务 P1-2b(2026-10-31 立项):消除中短睡眠档唤醒闪断

### 8.1 背景

P1-2 主任务(已验收)的触发阈值 `CLOCK_JUMP_GUARD_MS = 300_000` 是**严格大于 5 分钟**才进入宽限期。睡眠 90s(PEER_TTL_MS)~5min 的唤醒走正常 TTL:peers 被正常删除、靠 announce(≤3s)重建,**闪断 ≤3s 依旧**——而这正是日常最高频的睡眠档(午休合盖、短时离开)。复现器:整机验收方案 S5([Doc/Rfc/整机验收实施方案.md](整机验收实施方案.md) §三.1)。

### 8.2 规格

1. **核心约束(评审将据此复核)**:任何足以让 peer 超过 TTL 的停顿,必须触发宽限期——即触发阈值必须 **< PEER_TTL_MS**(当前 300_000 > 90_000 违反此约束,是缺口根源)。
2. **推荐改法(最小)**:`CLOCK_JUMP_GUARD_MS` 300_000 → **60_000**,更新注释:prune 调用正常间隔 ≤2s(发现线程 500ms tick + 前端 2s 轮询),间隔 >60s 只可能是进程挂起(睡眠)或时钟跳变;宽限期代价(≤5s stale 容差)相对 90s TTL 可忽略。可顺手改名为 `PRUNE_GAP_GRACE_TRIGGER_MS` 以贴合语义(非必须)。
3. **允许备选**:「prune 间隔 > N×announce 周期」式触发,但必须满足核心约束并在交付说明中论证;**结构不动**:`peer_stale`/`PRUNE_GRACE_UNTIL_MS`/宽限期语义保持现状,只动触发阈值。
4. **新增测试** `grace_triggers_for_sub_five_minute_suspension`:构造 120s 的 prune 调用间隔(模拟 2 分钟睡眠)→ 触发宽限、宽限内不删、announce 续命后回归正常 TTL。既有测试均按常量符号取值,应零改动自适应;若发现 300s 硬编码一并修正。
5. **顺手修日志措辞**(上轮记录项):`discovery prune expired N peers after grace` 改为仅在宽限期实际参与淘汰时打印(如记录 grace_until 是否非零且刚越过),或改为中性措辞 `discovery prune expired N peers`。
6. **真机衔接**:合入后整机验收 S4、**S5 均为阻塞级、预期无闪断**(方案文档已同步更新判级)。
