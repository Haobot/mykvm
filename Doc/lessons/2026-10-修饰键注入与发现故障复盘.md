# 2026-10 修饰键注入与设备发现故障复盘

> 范围：Windows 控制 macOS 场景下（1）按住 Command 类功能（微信输入法语音识别）不触发；（2）替换 `.app` 后 Win 端扫描不到 Mac。
> 涉及提交：`12e34dc`（注入修复）、`220cabd`（发现加固）。
> 结论先行：两个问题都是"系统事实与代码假设不一致"——macOS 合成键盘事件缺少物理键盘才有的**设备相关修饰键位**；macOS 在 app 包被替换时会重启**本地网络隐私会话**，启动瞬间的阻塞 `sendto` 能把发现线程永久卡死。后者与业务逻辑无关，但必须靠启动顺序与 socket 超时防御。

## 1. 现象

### 1.1 按住 Command 不触发微信输入法语音

- 拓扑：`PROART16`（Windows，192.168.3.172）= 服务端/控制端；`MacBook-Pro`（macOS，192.168.3.45）= 客户端/被控端。
- Win 端开启跨平台改键：Alt → Command（其余 Control/Alt/⌘ 对调）。
- **Alt+C / Alt+V 复制粘贴正常**；但按住 Alt（Mac 上的 Command）超过微信输入法（WeType）长按阈值（实测约 1.2s）时，语音面板不出现、麦克风不被占用。
- 物理 Mac 键盘按住 Command 则正常 —— 说明 WeType 功能本身可用，差异只在"远端注入的事件"。

### 1.2 重建安装后 Win 端扫描不到 Mac

- 16:14 安装新构建后，Win 端设备扫描不到 Mac；但 Win → Mac 的鼠标/键盘输入仍然可用（QUIC 连接已建立，走的是已有 peer 地址）。
- 旧应用被替换前一切正常；杀掉应用重新打开即可恢复。

## 3. 根因

### 3.1 注入的修饰键事件缺少设备相关位（主因）

- 物理键盘的 `flagsChanged` 事件同时携带两类位：
  - 设备无关位（Cocoa）：Shift `0x00020000`、Control `0x00040000`、Option `0x00080000`、Command `0x00100000`；
  - 设备相关位（IOKit `NX_DEVICE*KEYMASK`）：Left Ctrl `0x1`、Left Shift `0x2`、Right Shift `0x4`、**Left Command `0x8`**、Right Command `0x10`、Left Option `0x20`、Right Option `0x40`、Right Ctrl `0x2000`。
- 旧实现 `windows_vk_to_mac_flag()` 只返回设备无关位，`MAC_INJECT_FLAGS` 里也只有它们；注入 Command 时 flags = `0x00100000`。
- WeType 的 `ShortcutKeyMonitor`（HID 层 active CGEventTap，监听 flagsChanged）按 keyCode 查设备位掩码后执行 `tst mask, flags → isDown`；keyCode 55（左⌘）掩码是 `0x8`。注入事件没有 `0x8` → 按下被判定成松开 → PTT 永不启动。
- **复制/粘贴为什么正常**：AppKit 的 key equivalent 只看后续字母键事件上的设备无关 `⌘` 位；mykvm 一直有盖这个位。因此"和弦能用、按住类功能不能用"。

**证据**：

- WeType 3.0.0 主二进制未加密、符号完整，`ShortcutKeyMonitor.handleFlagsChanged`（VA `0x1001a9f34`）里能读到 `0x8/0x10/0x1/0x2000/0x20/0x40/0x2/0x4/0x800000/0x10000` 的掩码表，以及 `handleCGEvent`（VA `0x1001afd90`）只对自身注入（`kCGEventSourceUserData` 为 `WTYPECMD/WTYPEVOI/WTYPEACT`）做 bypass，不会过滤 mykvm 的合成事件。
- 受控实验（与注入完全相同的 `CGEvent(keyboardEventSource:virtualKey:55,keyDown:)` + `set_flags` + `post(.cghidEventTap)`）：

| 轮次 | 注入 flags | 结果 |
| --- | --- | --- |
| A | `0x00100000`（仅设备无关） | WeType 无反应 |
| B | `0x00100008`（补左⌘设备位） | 约 1.2s 后 WeType 申请麦克风（TCC 日志 `com.tencent.inputmethod.wetype`） |
| C | `0x00100000` | 无反应 |
| D | `0x00100008` | 再次申请麦克风 |

- WeType 当前配置从 `~/Library/Application Support/WeType/mmkv/wetype.settings` 解出：`voicePTTHotKey=1`、`voicePTTShortcut_keyCodes=[55]`（左 Command）、`tapCount=1`，与用户设置一致。

### 3.2 重装后的 local-network 隐私会话重启 + 阻塞 sendto（主因）

- 替换 `.app` 会让 macOS 在同一秒重启本地网络隐私会话：系统日志
  `nesessionmanager: NESMPathControllerSession[com.apple.preferences.networkprivacy-…]: Handling installed apps change, restarting`，
  紧跟 `nehelper: Local network allowed by preference for mykvm (com.xzhpl.mykvm), but received prompt. Clearing cached UUIDs and restarting session.`
- 应用启动后立即做第一次 announce（旧代码 `last_announce = now - 10s` 强制立即发送）；该阻塞 `sendto` 撞进会话重启，在内核里不再返回。
- 发现线程同时承担"发送 announce / 探测已知 peer"和"`recv_from` 收包/回 reply"；首个 `sendto` 卡死 → 整条发现链路沉默：不广播、不收包、不回 probe，因此 Win 端扫描不到；QUIC 输入因连接已由 Win 端发起而继续可用。
- **证据**：`sample 24597 2` 的线程栈停在
  `start_discovery → send_discovery_packet → UdpSocket::send_to → __sendto`，且持续 26 分钟不返回；同期 Windows 广播抓包正常（每 2–3s），应用却无任何 announce 发出、无 peer 更新日志。
- 重启应用后立即恢复（说明不是代码逻辑死循环，而是 socket 调用被系统状态卡住）。

### 3.3 附带的 UX 坑：跨平台改键的方向性

- 修改键映射由**发送输入的一端**应用（sender-side）。被控端 `layout.json` 里的 `modifierMap` 对"接收方向"不起作用。
- 本次现场 Mac 端也保存了 `alt→meta` 配置；排查时必须确认映射设置在对端（控制端）。建议 UI 在 client 角色隐藏该卡片或注明方向。

## 4. 修复内容

### 4.1 `12e34dc` fix(注入)：补齐设备相关修饰键位

- `windows_vk_to_mac_flag` → `windows_vk_to_mac_flags`：每个修饰键返回 `设备无关位 | 设备相关位`，按左右分侧（LWin→左⌘ `0x8`、RWin→右⌘ `0x10`；左右 Shift/Ctrl/Alt 同理）。
- `inject_key` 与滚动注入由 `CGEventFlags::from_bits_truncate` 改为 `from_bits_retain`：core-graphics 的 `CGEventFlags` 只声明设备无关位，`truncate` 会静默丢弃 `NX_DEVICE*KEYMASK`（这是最容易"改了却无效"的坑）。
- 单测覆盖各修饰键精确位值，并加回归断言：`from_bits_truncate` 丢设备位、`from_bits_retain` 保留。

### 4.2 `220cabd` fix(发现)：防发现线程被阻塞发送卡死

- 发现 socket 增加 **500ms 写超时**：阻塞 `sendto` 会返回错误而不是永久卡死。
- **首次 announce 延迟到启动 3s 后**（原为启动即发），避开 app 包替换触发的隐私会话重启窗口。
- announce 发送失败落 `log::debug!`，便于下次定位。

## 6. 经验与教训

### 技术

1. **合成输入要"像硬件"**：普通快捷键只需要设备无关 flags，但"按住修饰键"类功能（IME 语音、sticky keys、部分游戏）看设备相关位。注入必须两套位都带，且左右分侧。
2. **bitflags 的 truncate 是隐形杀手**：未声明的位会被静默丢弃。凡是往 `CGEventFlags` 塞自定义位，先确认 API 用的是 `from_bits_retain`（或直接走裸 FFI）。
3. **系统行为也是外部依赖**：macOS 15+/26 的本地网络隐私由 nehelper/NESMPathController 管理，**app 包被替换（更新/重装）时会重启会话**；启动瞬间的阻塞网络调用可能永久挂起。长驻线程的任何网络 syscall 都应有超时，并避免在系统状态切换的同时刻发第一个包。
4. **"发+收同线程"会放大故障**：任何一次阻塞发送都会让收包路径一起停摆，表现为"对端完全发现不了本机"。发现/心跳这类线程应保证收发互不阻塞（至少全部 socket 调用带超时）。
5. **用副作用做观测**：TCC 麦克风访问日志是判断 IME 是否真的激活的可靠信号；`sample` 线程栈能一锤定音区分"卡在系统调用"还是"业务死锁"；`CGGetEventTapList` 能看清谁在 HID 层监听。
6. **闭源二进制也能给出根因**：WeType 是未加密、符号完整的 Mach-O，`nm` + `lipo -thin` + `llvm-objdump` 可直接确认检测逻辑。把反汇编结果当数据证据，不执行、不注入其进程。

### 流程

1. **先固定现场事实，再读代码**：角色/拓扑、改键在哪端生效、物理键盘对照，这三件事能砍掉一半排查空间。
2. **对照实验胜过"应该可以"**：A/B 两轮 + 外部可观测副作用（麦克风）比任何推断都可靠。
3. **重装/重签名是高风险动作**：同时影响 TCC（辅助功能/输入监控/本地网络）与系统网络会话。安装后应立刻按清单验证：无权限告警、发现正常、输入正常、IME 按住类功能正常。
4. **修复要闭环到真机验收**：构建通过、单测全绿只是必要条件；用户确认"正常"才算完成。
5. **提交拆分**：注入修复与发现加固分开 `fix:` 提交；复盘用 `docs:`（避免触发发版）。
6. **注意仓库的发版约定**：push 到 `main` 会触发 Release workflow；`fix:`/`feat:` 会发版，纯文档/工具链提交用 `docs:`/`chore:`。

## 7. 改进建议

- **P0 安装自检**：`scripts/install-mac-app.sh` 安装后检查日志是否出现 `discovery peer updated`，异常时自动重启一次应用并提示。
- **P1 发现看门狗**：本轮用写超时兜底；可在发现线程加心跳 watchdog（心跳停滞 → 重建 socket/线程），覆盖其它潜在阻塞点。
- **P1 输入回归**：把"IME 按住修饰键激活"加入 macOS 真机验收清单（微信输入法/豆包输入法），并保留受控 CGEvent 对照脚本作为回归工具。
- **P2 UI**：client 角色隐藏或说明"跨平台改键仅对发送方向生效"。
- **P2 文档**：README/权限说明补充"重装本地自签名构建后 TCC/本地网络可能重置"的排查步骤。

## 8. 排查工具箱（本次实际使用）

- 日志/配置：`~/Library/Logs/com.xzhpl.mykvm/mykvm.log`、`~/Library/Application Support/com.xzhpl.mykvm/layout.json`。
- 进程栈：`sample <pid> 2 -file /tmp/sample.txt`。
- 系统侧日志：`log show --last 30m --predicate 'subsystem == "com.apple.TCC"'`、`eventMessage CONTAINS "networkprivacy"`、`process == "nehelper"`。
- 事件 tap 清单：Swift 调 `CGGetEventTapList`，看 location/options/mask/enabled 与 owner pid。
- 合成事件观测：自建 HID `CGEventTap` 记录 `type/keycode/flags/srcPid`；发送端用 `CGEvent(keyboardEventSource:virtualKey:keyDown:)` + `set_flags` + `post(.cghidEventTap)`。
- 发现协议抓包：Python socket `SO_REUSEPORT` 绑 47833 观察 announce/probe；msgpack 手工编码 probe 验证 responder（5ms 回 reply）。
- WeType 配置：解码 `~/Library/Application Support/WeType/mmkv/wetype.settings`（MMKV：key 长度+key+value 长度+value，字符串值内部再带一层长度）。
- 反汇编：`lipo -thin arm64` 出单架构，`llvm-objdump --disassemble --start-address=… --stop-address=…`，配合 `nm -n` 找函数边界。
