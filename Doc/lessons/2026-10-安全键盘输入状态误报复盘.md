# 2026-10 macOS 安全键盘输入提示误报（常驻弹窗）复盘

> 范围：Windows（PROART16）控制 macOS（MacBook-Pro）时的客户端场景——MyKVM 窗口反复弹出
> 「检测到 macOS 安全键盘输入(Secure Keyboard Entry)已开启……」且关闭后约 2 秒再次弹出，
> 而当时系统里并没有任何应用占用安全输入。
> 涉及提交：本轮 `fix(注入)`（实时探测 + 前端去重/自动清除）、`docs(复盘)`。
> 结论先行：提示文字本身没错，错在**状态是快照**。inject 阶段状态只在 `start_input` 时计算
> 一次并存入 `RuntimeStatus`，之后 UI 每 2 秒轮询都读到同一份旧值；再加上前端轮询每次都用
> 同一条 detail 调 `setErrorMessage`，用户关掉弹窗后 2 秒内又被重新打开——看起来就像"从来没关过"。

## 1. 现象

- Mac 端（client，`inputMode=receive`，已配对 PROART16）MyKVM 窗口出现「操作失败」弹窗，
  内容为 Secure Keyboard Entry 提示；点击右上角关闭后**约 2 秒重新出现**，一直无法摆脱。
- 同期用独立的 Carbon 探针（`IsSecureEventInputEnabled()`）确认系统当前**并未开启**安全输入。
- 日志里最后一次 `input inject unavailable` 是 2026-10-21 01:23（由某次 `start_input` 触发），
  此后三天应用既没有重启 runtime，也没有再打过这条日志，但弹窗一直在——状态明显是"陈旧的"。

## 3. 根因

### 3.1 后端：inject 状态是启动快照，不是实时状态

- `AppRuntime::start_input` 调用 `input::start_input_runtime`，把 inject 阶段状态算好后写入
  `self.runtime`；`runtime_status_for_layout()` 供 UI 每 2 秒轮询使用，但只重新计算
  discovery / clipboard / pairing / privilege / input_protection，**从不重算 inject**。
- 触发时机很隐蔽：应用登录自启时会**在 .setup 里立即 eager start** discovery + input；
  此外改设置（`restart_runtime_if_running`）也会重新 `start_input`。只要那一刻系统恰好处于
  安全输入状态（锁屏/登录窗口、密码输入框、密码管理器、终端勾选 Secure Keyboard Entry 等），
  该错误状态就会一直留在 `RuntimeStatus` 里。
- 反方向也有问题：用户之后去系统设置授权辅助功能、或关掉占用安全输入的应用，状态也不会自愈。

### 3.2 前端：轮询无条件重开弹窗

- `refreshRuntime()` 每 2 秒执行：`if inject.state === "error" { setErrorMessage(inject.detail) }`。
- 用户点关闭 → `errorMessage=null` → 下一次轮询（≤2s）又设回同一条文字 → 弹窗重新出现。
  由于 detail 是同一字符串，用户无法通过关闭摆脱它，这就是"一直提示"。

## 4. 修复

- `input.rs`：新增 `pub fn input_inject_status(layout)`（= `input_receive_status(layout, false)`，
  不带一次性授权弹窗），并在 `macos_secure_input_enabled()` 里按状态翻转打日志：
  `turned on`（WARN）/ `turned off; keyboard injection resumed`（INFO）。
- `lib.rs`：`runtime_status_for_layout()` 在 `started && input_mode == "receive"` 时用
  `refreshed_inject_status(...)` 每次重新探测（含 QUIC transport 就绪检查）；停止或控制端模式
  仍沿用快照。纯函数 + 单测覆盖"运行中必须用新探测值 / 停止或控制端沿用快照"。
- 前端新增 `src/runtimeBlocker.ts`：`blockingRuntimeDetail()` 统一 capture→inject 优先级；
  `trackRuntimeBlocker()` 让**同一阻塞原因在一次出现期间只弹一次**，条件解除时返回
  `clear` 自动关闭仍显示的弹窗，并重置以便下次出现时重新提示；`dismissRuntimeBlocker()`
  记录用户关闭。`App.tsx` 的 2s 轮询、手动启动、弹窗关闭按钮全部走这套逻辑。
  （手动启动/停止会重置 tracker，保证用户主动操作时重新看到失败原因。）
- 提示文案同步改为"关闭来源后此提示会自动消失，无需重启 MyKVM"，并补充锁屏/登录窗口来源。

## 5. 验证（本机实测）

- 单测：`cargo test --lib` → **218 passed**；`npm test` → **27 passed**（新增 6 个
  runtimeBlocker 用例）；`npm run build`、`npm run lint` 通过。
- 安装新版后：窗口无遗留弹窗；`IsSecureEventInputEnabled()=0`，日志无 inject 错误。
- 端到端（用 `EnableSecureEventInput()` 模拟，40s/60s/12s 三轮）：
  - 打开安全输入后 ≤2s：窗口出现新文案弹窗，日志
    `macOS Secure Keyboard Entry turned on; injected key events are dropped …`；
  - 关闭安全输入后 ≤2s：弹窗自动消失，日志 `… turned off; keyboard injection resumed`；
  - **弹窗出现后点击关闭**，在安全输入仍开启的 10 秒内截图逐字节一致——不会重新弹出；
  - 条件解除后再开启安全输入：弹窗重新出现一次（新一轮出现），解除后再次自动消失。
- 结论：`IsSecureEventInputEnabled()` 探针、实时状态读取、前端去重与自动清除三条链路均按预期工作。

## 7. 经验

- **凡是"系统当前状态"类的阶段状态（权限、安全输入、锁屏、输入法状态），都不能用启动快照去回答
  轮询**；状态读取路径要能随时重新探测，并在探测变化时记录日志。
- **可恢复的阻塞条件不要用"每轮重新 setError"来展示**：轮询会把用户关闭的弹窗当成新错误重新打开。
  展示层要记录"本轮出现已展示/已被用户关闭"，并在条件解除时自动清除。
- eager start 让应用在登录早期就启动输入链路，这个窗口期很容易撞上锁屏/登录窗口的安全输入状态，
  所以"启动即错误"的场景必须可自愈，否则用户会看到永久误报。
